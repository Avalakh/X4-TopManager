# Диагностика разработки

## Короткие командные сценарии

`crew_remote_prepare` один раз создаёт источник с native service crew на доке
HQ и отдельный недокованный корабль в20–25km. `crew_remote_transfer` вызывает
production RequestTransfer для выбранного реального person/seed; отдельный
attempt marker запрещает повтор неизвестного результата. `crew_remote_read`
проверяет exact receipt binding, source/target membership, seed, role и native
transit/scheduled/pod flags. Прибытие и production receipts не подставляются;
неподтверждённый путь остаётся pending/unknown. Старые role/bulk receipts и
no-replay markers не сбрасываются ради нового сценария.

`save_remote_personnel` использует тот же native save-list/free-slot путь, что
checkpoint, с отдельным marker для нового сценария. Он не очищает прежний marker
и не перезаписывает006/005/004/autosave. Requested не доказывает готовый файл:
нужны file/gzip/native list и последующий exact employee read-back.

`economic_search_start` один раз на сохранённый диагностический State запускает
настоящий Request_Commandeerable_Freighter дляenergycells в сектореHQ. Не включает
purchase fallback и не подменяет кандидатов, claims или результат. Активный
Governor и contextual search cue обязательны. `economic_search_read` читает
курсор/фазу/завершение и реальный Ship/order claim. После отрицательной отмены cue
результат finished/exhausted остаётся в ActionDefinition. Ответ
context_unavailable/effectsfalse не создаёт State и допускает проверку после
инициализации; previous_attempt и неизвестный ответ запрещают повтор эффекта.

`short_scenarios.py --output-dir <новый каталог>` после загрузки мира выполняет
одну подготовку hire_setup, один hire_scenario только при новом prepared,
одну military_setup и4 чтения с интервалом10s. Один процесс владеет role pipe;
ответ записывается сразу после каждого запроса. Unknown и повторная подготовка
не сбрасываются, эффекты не повторяются. Скрипт собирает факты, не выставляет
успех или принятие задач по одному sent. Дальнее прибытие персонала за пределами
этих чтений остаётся непроверенным; это не замена полному автономному прогону.

`military_setup` один раз меняет владельца одного известного бесхозного сектора
на player через штатный set_owner (тот же механизм в setup debug achievement).
Выбор ограничен16 секторами; чужие территории и отношения фракций не меняются.
Sent записывается до эффекта, actual owner определяет observed/unknown; повтор
не изменяет второй сектор. Команда не запускает и не подменяет цель Hold Space:
нужен отдельный read-back самостоятельного штатного решения управляющего.
Команда предназначена для подготовки тестового мира; в релиз она не входит.

`hire_candidates` только читает ограниченную страницу реальных NPC: показывает
hire fee, seed, роль, возможность найма, перемещение и источник. Отсутствие
кандидата в странице не означает отсутствие во всей галактике.

`hire_setup` один раз подготавливает тест: создаёт recruitable NPC в штатном
слоте известной аргонской станции, рассчитывает цену через
NPC_Instantiation.CalculateNPCHiringFee и создаёт тестовый разведчик у станции.
Бесплатное создание — только подготовка мира в диагностическом расширении;
игровой мод не получает этот способ приобретения кораблей или сотрудников.
Ответ содержит фактического капитана: создание корабля само по себе не доказывает
свободную должность. Повтор команды читает прежнюю попытку, не создаёт второй тест.

`hire_scenario` один раз передаёт подготовленного NPC и корабль в продуктовый
RequestHire с настоящими средствами игрока. Ответ sent не считается успешным
наймом: через `role` нужны receipt, реальная оплата, назначение и прибытие.
Unknown не очищать ради повторной покупки. Вакантность, вместимость, доступность
кандидата и живой персональный goal проверяет игровой мод.

`station_budget_setup` подготавливает финансовую нехватку только на заранее
определённой тестовой станции и возвращает фактические балансы. Не снимает
торговые ограничения игрока, не выдаёт деньги и не выполняет продуктовую оплату.

По текущему разрешению пользователя используется тестовое сохранение без
обязательной дополнительной копии. Команды не должны перезаписывать другие слоты.
Долгий автономный сбор запускать после завершения реализации и коротких сценариев.

`save_checkpoint` создаёт одно диагностическое сохранение в первом свободном
штатном слоте при активном управляющем. Собственный маркер запроса сохраняется
до вызова SaveGame; повтор не выполняется, старый `save_validation` не сбрасывается.
Ответ requested подтверждает только запрос: перед загрузкой проверяются файл,
целостность gzip и доступность в штатном списке. Для проверки нового назначения
checkpoint запрашивается только после реального observed прибытия сотрудника.
CLI `--save` принимает штатный формат имени, а существование и допустимость
сохранения дополнительно проверяет игровой save-menu. Произвольные пути не принимаются.

`lifecycle.py --output-dir <новый каталог>` выполняет один игровой сценарий
остановки и повторного назначения прежнего управляющего через существующий pipe.
Нужны загруженное тестовое сохранение и диагностический State с назначенным
сотрудником. Команды изменения выполняются ровно один раз; повторяются только
чтения ожидания active. Каждый ответ сохраняется до проверки. Проверяются полный
охват кораблей, отсутствие claims после остановки, прежний сотрудник и менеджер
станции, тот же индекс/сервис и число фракций в патрульной регистрации после
повторного запуска. Не проверяет оплату, потерю собственности, другого сотрудника
или двухчасовое управление. Не входит в поставку и не перезаписывает сохранение.

`station_fixture` — адресная проба штатного prefab construction-пути. Один раз
на загруженное состояние создаёт станцию игрока без готовых модулей по обычному
аргонскому advancedcomposites prefab-плану, в 20–40 км от HQ. Не вызывает process_build,
не выдаёт материалы/деньги/персонал. Повтор команды только читает ту же станцию.
Ответ содержит реальную очередь, число модулей, buildstorage, buildplot и деньги;
issued без Station считается неизвестным результатом и не повторяется.
Команда предназначена для текущего тестового сохранения и не входит в релиз.

Не входит в игровой релиз. Внешний Python процесс нужен только во время испытания,
игровой управляющий не получает решений через pipes.

`probe.py` — один общий клиент для списка/загрузки сохранений и адресной пробы
сотрудника. Требует Windows Python с pywin32 под владельцем процесса X4.
`named_pipe.py`, `base.py`, `runtime_user.py` перенесены из собственной прежней
реализации; импорты локальные, код приложения не запускается.

`extension` устанавливается отдельно как `extensions/tm_empire_diagnostics`.
Содержит собственную исправленную DLL транспорта и ограниченный Lua/MD клиент;
файлы Mod Support APIs не изменяются. Основной установщик эту папку исключает.
Разрешены только фиксированные команды; выполнения произвольного Lua/XML нет.

Порядок адресной пробы: загрузить разрешённое тестовое сохранение через `load`,
считать `role`, выполнить `assign` одного существующего service-crew NPC на
собственную станцию как passenger. `assign` не заменяет менеджера станции.
Дождаться штатного перемещения; `place` инстанцирует именно переведённого человека
из его шаблона в комнате станции. `role` только читает, не инстанцирует NPC.
`save` использует только предварительно свободный слот save_004.
Ответ accepted/sent не доказывает прибытие, размещение или успешную запись save.
После испытаний расширение удалить; собственные NPC мода должны оставаться
в основном игровом состоянии, а не в диагностическом namespace.

Проба пока проверяет отдельного человека на станции. Она не является
доказательством module binding, пользовательского назначения или готовности AI.

Сведения по первому запуску: текущая игра 9.00 (611726), схема MD проходит
`tools/validate_md.ps1`; резервная копия autosave_03 имеет SHA256
`8E9E1809F07E67BAE5E72ED5B2C2A3808694F69D89A57E86F6ED259591228521`.

Команда module добавляет готовый tm_empire_control_arg_macro на принадлежащую игроку HQ, найденную по штатному исследовательскому модулю. Повторный вызов возвращает существующий модуль; ответ содержит результат повторного find_module. Мгновенное создание разрешено пользователем только для тестов.

purchase_fixture — адресная проба обычной покупки одного аргонского курьера
на известной верфи, найденной по canbuildfor/player и доступному blueprint.
Использовать в отдельной save_004 после резервирования исходного save.
Вызывает штатные buttonAddPurchase/buttonConfirm; реально расходует деньги
и создаёт обычную ресурсную очередь. Не сохранять результат поверх исходного
пользовательского save. Ограничения: price <= 2000000, достаточный баланс,
crewprice=0, пустая корзина, одна попытка в State до её согласования. Повтор
отклоняется даже после неизвестного исхода; сбрасывать Stage командой нельзя.
Проба не подключена к production AI и не заменяет его платёжный адаптер.
build_contract читает последний native ship build из игрового события и
TrackBuild/ObserveTracked, не создаёт новых заказов и не платит.

purchase_native проверяет тот же один фиксированный курьер без открытия меню:
native quote → native plan → Helper.callLoadoutFunction → обычные
TransferPlayerMoneyTo/AddBuildTask6/SetBuildTaskTransferredMoney. Перед
созданием задания проверяется фактическое списание; ошибка после оплаты
сохраняет sent и не разрешает повтор. Native receipt хранит точный ID из
AddBuildTask6; MD handle допускается к TrackBuild только после его совпадения
с возвращённым ID, верфью, player faction, macro и ценой. Команда остаётся
диагностикой на исходном отдельном save_004, не production управлением.

`role` дополнительно возвращает `governor_transfer`: состояние отдельного
назначения управляющего, actor/source/person/station/module, issued, move_sent
и текущую причину Pending. Это только чтение production TM_Empire_Roles.Pending;
запрос не отправляет перевод, не снимает должность и не меняет unknown.
Состояние idle означает отсутствие ожидающего назначения: оставшиеся поля
могут описывать предыдущий перевод и не доказывают новую отправку. При sent
или unknown идентичность и факт прибытия проверяются отдельно по binding,
сотруднику станции и отсутствию исходной записи. Счётчик не является приёмкой
назначения через пользовательский диалог либо save/load.

`role` возвращает до двух `personnel_arrival` строк для существующих hire/transfer
receipts: ожидаемые actor/template/seed, target/post, реальный occupant controlpost,
его roleobject/container/station и transit/scheduled, source membership и reason.
Для hire person может не храниться: source_member=not_recorded обозначает
отсутствие этого доказательства, а не отсутствие человека. Для crew-role перевода
controlpost occupant отсутствует; такая строка не доказывает прибытие экипажа.
Проба только читает существующие квитанции, не вызывает ObserveHire/ObserveTransfer
и не запускает назначения. Отсутствие строки означает отсутствие receipt.

`personnel_transfer` — однократная изменяющая проба, только в разрешённом тестовом
сохранении. Выбирает среди первых128 кораблей одного существующего свободного
члена service crew и другой operational корабль с people.free, исключая
player.controlled. Вызывает production RequestTransfer с действующим Manager
и его реальной целью; не создаёт шаблонов, денег или должностей. Marker попытки
записывается перед вызовом, повтор в этой сохранённой сессии отклоняется даже
при отказе/тайм-ауте. Результат sent не означает прибытие. Следующий шаг —
readonly role/receipt и штатное ObserveTransfer; положительное crew arrival
нужно подтвердить target/source membership, role и отсутствием transit.
MD XSD/scheduling проходят. Проба подготовлена, не установлена и не исполнена.

`observe_crew_transfer.py --person <MD template> --target <MD component>
--output-dir <новый каталог под .cache/tmp> [--timeout 600]` наблюдает только
конкретный ранее отправленный crew transfer. Пользуется общими NamedPipeServer,
probe.request и parser lifecycle.fields. Каждая сырая role-квитанция сохраняется
до проверки. passed требует одновременно production state=observed, person/target
соответствия, реальной целевой people-записи с ожидаемой ролью, transit=0,
scheduled=0 и source_member=0. Отсутствующая/изменённая receipt — ошибка;
истечение времени — status=unverified без повторной отправки. result.json
сохраняется и при ошибке. Этот runner не запускает personnel_transfer_fixture,
не доказывает save/load/наём/все кадровые сценарии. Ожидание подключения общего
pipe может длиться отдельно от таймера опроса: при отсутствии ответа проверять
живой handle, не перезапускать игру только по истечению наблюдения.
Новый runner прошёл py_compile; игровое исполнение ещё не выполнялось.
Readonly role дополнен crew_arrival с реальной target people-записью/ролью/
транзитом и исходным membership; диагностический MD XSD/scheduling проходят.

После save/load используйте `--target-idcode MZK-812`: внутренние component handles могут измениться. Наблюдатель связывает постоянный idcode с единственным текущим ship handle из той же read-квитанции, затем проверяет target квитанции и person. Неоднозначный или отсутствующий ship прекращает проверку без dispatch. `--target` годится только для handle текущей загруженной сессии.

`training_positive_fixture` — однократная диагностическая команда: при отсутствии подходящего предмета добавляет один семинар в тестовый инвентарь и вызывает production RequestSeminar. Отдельный saved marker запрещает повтор; seeded/inventory-before/after/skill-before/after и независимость manager возвращаются вместе. Не входит в production package, не меняет звёзды вне штатного seminar action. Использовать только для согласованного тестового сохранения. `provision_read` дополнительно сообщает stock production flags и наблюдаемые finished-cycle events; null не означает нулевой выпуск.

`local_owned_builder` — подготовка собственного штатного аргонского
застройщика в5–7км от buildstorage текущей queued expansion. Использует тот
же одноразовый guard, что local_builder: если уже есть assigned constructor
или sent/unknown квитанция этого задания, spawn запрещён. Создаёт корабль
со штатным пилотом/30 строительными дронами и default Wait; дальнейшее
назначение остаётся production RequestOwnedBuilder/штатному AI. Не вызывает
deploy, process_build, сброс квитанций, выдачу материалов или платежи.
Это тестовая собственность, её создание не квалифицирует покупку корабля.

`construction_blueprint_prepare` выдаёт только чертёж управляющего модуля
через штатный add_blueprints для подготовки строительной пробы в раннем
сохранении. Денег, лицензий, планов или квитанций не меняет; ответ сообщает
world_fixture=true/purchase_called=false. Не квалифицирует обычную покупку
чертежа. Далее production проверяет полный план обычным путём.

Owned режим local_owned_builder допускает подготовку также во время
validating текущей expansion активного Manager/существующей goal. Это
устраняет гонку с автоматическим hire после появления очереди. NPC режим
по-прежнему требует queued/existing build; старые sent/unknown/назначенный
constructor блокируют оба режима. После prequeue подготовки назначение
и реальные эффекты выполняет только обычный production путь.

`save_validation` использует только свободный save_009, после свежего
штатного списка (занятый/недоступный слот запрещён) и active governor
projection. Перед SaveGame сохраняет no-replay intent. Requested не
подтверждает запись; нужен файл/native list read-back и load save_009.
Save_004/autosave_01 этой командой не затрагиваются. Команда предназначена
для пакетной проверки binding/queue persistence, не входит в релиз.


### Короткая проверка снабжения и свободного сохранения (736–737)

`supply_setup` подготавливает один собственный S scout с пилотом у известной
доступной NPC-верфи. Это бесплатная подготовка мира, а не покупка корабля.
Незавершённая supply квитанция препятствует подготовке; её не сбрасывают.
`supply_quote` один раз вызывает production QuoteRestock для одного обычного
спутника с лимитом min(1000000Cr, player.money). `supply_step` вызывает
production StepRestockDelivery: обычную оплату/очередь/согласование, а не
добавление боеприпаса командой. `supply_read` только читает исходную квитанцию,
цену, фактический запас и платёж. Отправленные/unknown эффекты не повторяются.
Эта проба проверяет адаптер снабжения; она не доказывает самостоятельное
решение военного флота и не заменяет итоговый автономный прогон.

`save_validation` выбирает первый свободный штатный save_NNN, проверяя
свежий native GetSaveList и активного управляющего. Существующий слот не
перезаписывается; requested требует подтверждения сохранения через список
и повторной загрузки. Старый save_fixture/save_004 для этого не использовать.
После repair_read736 контекст и результат находятся в одном сообщении;
несовпадение префикса для repair/supply/service команд останавливает пакет.


Production741 сохраняет MD buildtoken в paid receipt; Lua записывает
recordedbuild только после проверки native GetBuildTaskInfo и учёта оплаты.
Supply read показывает token, типы и сравнение native/Lua build references.
При старом платеже без связанного token возвращается unknown; это не
разрешение повторно оплачивать или создавать очередь.


`crew_docked_prepare` (source746) создаёт два тестовых scout в одном
штатном docking storage у известной NPC-верфи из SupplyScenario: исходный
с настоящими native service people, целевой со свободными местами. Не меняет
isintransit/role/arrival, не вызывает transfer и не сбрасывает production
квитанции. Затем existing personnel_transfer_fixture выполняет обычный
RequestTransfer/PerformCrewExchange2. Подготовка запрещена при sent/unknown
или уже использованной паре; world_preparation_unconfirmed не разрешает
перевод. Это позволяет отдельно проверить native same-station route без
долгого ожидания pod или вмешательства в флаги прибытия.
## Пакет ownership управляющего

Wire-команды `governor_ownership_loss`, `governor_ownership_read`,
`governor_ownership_restore` проверяют утрату владельца одного реального
сотрудника. Не меняют владельца станции, не уничтожают NPC и не сбрасывают
квитанции. Loss/restore имеют отдельный сохранённый запрет повторного эффекта;
restore требует того же seed/станции/модуля. Read сообщает actual старый cue,
authority, UI и независимый station manager. Это не проверка разрушения модуля
или продажи станции. Команды доступны только в диагностическом расширении.

## Смена менеджера станции и периоды

`station_manager_vacate/replace/read/restore_prepare/restore` используют native assign_hired_actor
с предварительным check=true. Source — оставшийся реальный service person
RemoteCrew.source, target — станция управляющего, post — station manager.
Native Conversations выполняет замену; diagnostic не dismiss-ит персонажей,
не устанавливает control slot, seed, arrival или оценку. Отдельные сохранённые
attempt guards защищают каждую фазу. Vacate переводит прежнего менеджера в
passenger той же станции, сохраняя identity. Replace допускается после actual
свободного post; restore_prepare таким же штатным переводом освобождает post
для исходного сотрудника. Read проверяет actual нового/старого
сотрудника, source membership, flags, неизменность governor/empire manager,
новый observation period и маркировку старой истории. При запрете native check
эффект не выполняется; исходный сохранённый checkpoint не перезаписывается.
