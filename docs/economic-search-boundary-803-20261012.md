# Граница порционного экономического поиска

Request_Commandeerable_Freighter в адаптированной экономике проходит LocalClusters,
Temp_PotentialShips и PotentialShips целиком. Штатные правила сохраняют приоритет
warebasket и допустимость собственного добывающего/транспортного корабля.

Механическое ограничение первых32 элементов меняет смысл отрицательного результата:
отсутствие корабля в выборке не означает отсутствие подходящего собственного актива.
После такого ложного отрицательного результата штатная ветка может перейти к покупке.
Поэтому простой cap, применённый военным целям, здесь не добавлялся.

Недостающий контракт для3.8: продолжаемый поиск в нескольких порциях с курсором
по пространствам/кандидатам, принадлежностью requester/ware/manager/периоду и
явным incomplete состоянием. До окончания поиска покупка удерживается; результат
не должен объявлять unavailable и не должен повторять уже отправленные эффекты.
После смены manager/потребности или исчезновения активов требуется пересверка.

Адаптировать только обход штатных кандидатов и отрицательную ветку; существующие
mining capabilities, ship guards, выбор назначения, оплата и receipts сохраняются.
Это установленная source граница, не подтверждение полной задачи масштабирования.

## Реализация805 — 12.10.2026

Воспроизводимый адаптер `batch_economic_ship_selection` в
`tools/adapt_native_manager.py` заменяет только обход кандидатов в
Request_Commandeerable_Freighter. Каждая порция выполняет не более32 шагов:
переход к следующему пространству, подготовка одного приоритетного кандидата
либо штатная проверка одного корабля. Между порциями задержка1s; курсор, списки
и фаза сохраняются в namespace исходного запроса. Полный список пространства
получается штатным find_ship один раз, а не повторно на каждом тике.

Приоритетный список полностью подготавливается перед выбором: вставка
warebasket-кандидатов в начало и добавление остальных пригодных кораблей в конец
сохранены. Проверки добывающего оборудования, tradeorders, cargo и общего
CanUseOwnedShip сохранены. Исчезнувшие/переданные другому владельцу корабли
пропускаются; утрата authority/requester или disregard прекращают запрос.

Штатный effect tail и его lifetime cues перенесены под однократное завершение
поиска с прежним namespace. Монитор ActionReports удерживает незавершённый
запрос, включая промежуток до выполнения completion; UI показывает ожидание,
а не отсутствие подходящих кораблей. Реальные приказы и квитанции остаются
в штатном адаптированном пути, перед ними сохранены повторные effect guards.

Непосредственная отрицательная ветка отменяет запрос. Переход к другой стратегии
зависит от последующего штатного анализа; немедленная покупка из этого cue
не утверждается. Предыдущая формулировка про покупку описывала риск последующего
перепланирования после ошибочного отрицательного результата.

Проверено805: сборка13 MD scripts, check_adapted_manager, все MD/AI schemas и
scheduling refs, Lua syntax. Это source checks, не игровое подтверждение
порционного обхода. Engine find_ship и list insertion остаются штатными
операциями над списком; ограничение относится к явному MD обходу, не означает
постоянную стоимость всех engine операций. Задача3.8 остаётся открытой.

Короткий пакетный сценарий: подходящий корабль после32 кандидатов; priority
warebasket порядок; полный отрицательный поиск; исчезновение корабля и смена
authority между порциями; отсутствие повторного эффекта после загрузки.

## Замыкание вызывающих веток806

Повторный source audit выявил синхронные потребители результата: две секторные
ветки принимали только наличие Ship, Upkeep provision и station factory сразу
переходили к покупке при его отсутствии. Source805 без этой адаптации был
незавершённым: pending запрос мог потеряться из reports или работать параллельно
с покупкой. Эта версия в игру не устанавливалась.

Source806 адаптирует все4 вызова. Секторные ветки принимают pending SearchCue
в обычный ActionReport; Ship-dependent debug сообщения остаются за проверкой
наличия корабля. Upkeep и factory регистрируют pending запрос и удерживают
непосредственную покупку. Только для этих двух исходных fallback веток полный
отрицательный поиск вызывает штатный Request_Freighter один раз, с прежним
ActionDefinition и актуальной authority. Покупка не введена в секторные ветки,
где её непосредственного fallback не было. Непроизводственный factory путь
сохраняет исходное непосредственное приобретение.

Отмена главной factory задачи помечает ожидающий search sub-action Disregard,
даже когда корабля ещё нет и native object signal отправить некуда. Очередная
порция отменяет такой запрос до исполнения.

Короткая offline проверка806 выполняет фактические XML caller actions с stub,
возвращающим только pending receipt: все4 не запускают преждевременную покупку,
reports/sub-actions сохраняются, непроизводственный factory продолжает штатную
покупку. Сценарий `.cache/tmp/station-boundary-20261011/caller_boundary806.py`
PASS. Это проверка caller control flow, не доказательство engine scheduling,
поиска, оплаты или save persistence. Build/check_adapted/MD+AI schemas и
scheduling refs также PASS.
