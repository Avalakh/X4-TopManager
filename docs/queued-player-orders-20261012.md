# Приоритет ручных приказов в очереди — source617

Существующий CanUseOwnedShip отклонял hasorderloop и флаги текущего order.
Short615 показал, что создаваемый ручной приказ может существовать в очереди,
когда текущий order ещё не имеет isoverride/haspriority. Проверка только
текущего приказа оставляла функцию игрока без подтверждённой защиты очереди.

Перед claims/effects shared guard теперь просматривает до32 queued orders.
Любой существующий приказ этого корабля с isoverride/haspriority даёт
manual_or_priority_order. Если очередь больше32, возвращается конкретное
order_queue_inspection_incomplete; неподтверждённая очередь не считается
доступным кораблём. Никакой приказ игрока не отменяется/не переписывается.
Свойства order подтверждены libraries/scriptproperties.xml:1699–1700.
Эта общая граница не заменяет повторную проверку Lua непосредственно при
оплате/другом асинхронном эффекте;3.7 остаётся открытой до полного пакета.

Diagnostic priority fixture проверяет конкретные сохранённые manual/priority
order handles, их принадлежность/присутствие в очереди/флаги. Передаёт в
CanUseOwnedShip настоящий действующий Manager cue в качестве контекста
проверки, без ожидания первого кадрового Tick. Эффект не выполняется;
guards собственности/lifetime/governor/manual остаются production.

Для original Manager диагностика дополнительно пишет его фактическое state,
результат ReadGoalLifetime и присутствие в Registry сразу после снятия роли.
Критерий stopped пока не ослаблен: complete родительского cue сам по себе
не доказывает ни остановку дерева, ни наличие второго активного исполнителя.
