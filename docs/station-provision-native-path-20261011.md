# Связь оценки обеспечения со штатной экономикой

Проверено по текущим исходникам 11.10.2026. Это аудит существующего пути, не новая приёмка 5.4.

## Уже существующий путь

Адаптированная копия tm_factionlogic_economy.xml записывает штатный InsufficientProductionWares в собственный отчёт. EvaluateSectorShortage использует именно этот отчёт: строки571–593 агрегируют значения по станции/сектору/товару. Выбор экономического действия сохраняет штатные пороги. Ветви1121/1131 сигналят Request_Commandeerable_Freighter, 1141/1153 — Request_Freighter. Тип Miner в исполнителе определяется Ware.hastag.minable. Действующий адаптер использует собственные assets/claims и оплачиваемую покупку вместо NPC job spawn. ReadStationEvidence использует тот же report для видимой нехватки ресурсов.

Следовательно, подтверждённая нехватка производственного ресурса уже доступна единственному штатному управляющему, независимо от открытия вкладки. Повторный dispatch из оценочного подмодуля не нужен и мог бы дать второй запрос на тот же дефицит. В этом аудите новый исполнитель/порог/запрос не добавлялись.

## Оставшиеся пробелы

Upkeep.Needs_Subordinate_Mining_Ship_Lib даёт список отсутствующих типов шахтёров, а observer сохраняет miningtypes. Этот список сам по себе НЕ доказывает достаточную производительность и НЕ доказывает, что штатный секторный выбор уже рассмотрел именно его. Недостаток бюджета тоже нельзя выдавать за выполненное пополнение. Для5.4 ещё требуется подтверждённый сценарий нехватки шахтёров, штатного рассмотрения перераспределения/приобретения один раз, read-back результата и сохранение обычного manager station slot. Обычная покупка транспорта в других сценариях не закрывает этот критерий.

Свежая игра PID20116 работает; последние provision243 подтверждают производство/ресурсную проблему KMT485, но mining=null/подчинённых0 и поэтому не являются нужным mining-сценарием. 8/32 задач остаются приняты.
