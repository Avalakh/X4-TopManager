# Копия Manager — этап изоляции

Текущий пакет: adapt_native_manager.py собирает целостное private замыкание
из12 scripts в native/adapted/md. native-manager-adapted.json содержит closure
с SHA, состоянием адаптации и конкретными cue/tag/attributes несовместимых
границ jobs/acquisition/assignment/finance/faction/personnel. Два scripts
имеют частичную адаптацию, остальные ещё сохраняют NPC границы. XSD и локальные
refs проверены; closure не является списком устанавливаемых/активируемых файлов.
Дальнейшая работа идёт по всему управляющему крупным пакетом с общей игровой
приёмкой, а не серией самостоятельных проб каждой изменённой строки.

Штатный Manager версии 18 скопирован в `native/md/tm_factionlogic.xml`, отдельный script `TM_Empire_FactionLogic`. Подготовлено 12 исходных scripts замыкания; `native-manager-copy.json` содержит исходные/новые SHA256, namespaces, внешние границы, начальные cue и эффекты. `tools/copy_native_manager.py` воспроизводит копию, `check_native_manager_copy.py` проверяет изоляцию и неизменность оригиналов.

Замыкание включает четыре зарегистрированные военные цели: Hold Space, Invade Space, PatrolCoordinationService и Plunder. Registry `$FactionGoals` является динамической зависимостью; её учёт указан отдельно от обычных текстовых md-refs. Неиспользуемая PrepareStagingArea не копировалась только из-за похожего имени. Общие штатные LIB_Generic и прочие внешние ссылки перечислены для проверки веток.

NPC startup `FactionLogicManagers` и общий ручной `Generate_Global_Report` не перенесены. Собственный `FactionSignalled` сохранён: он ожидает явного сигнала, не содержит действий и нужен дочерним обработчикам Manager. Проверка копии контролирует наличие целей собственных прямых cue/ref ссылок. Stateful md-refs перепривязаны в собственное замыкание. Глобальные managers/goals/economy/deployable/metadata tables изолированы. Общая `md.$SystemTimeAtGamestart` остаётся только источником времени. NPC scripts, их регистрация и файлы базовой игры не изменены.

**Эта копия пока не установлена и не выполняется.** Папка native не входит в allowlist игрового установщика. XSD всех 12 файлов проходит, но задача 3.1 ещё открыта: требуются адаптация несовместимых эффектов, собственные входы/данные и отдельный работающий экземпляр игрока. Наличие исходников не доказывает работающий AI.

## Следующие конкретные границы

Первый адаптированный слой воспроизводится `tools/adapt_native_manager.py`
от исходной изолированной копии в `native/adapted/md`. Для Manager штаб
привязан к `$GovernorStation`; NPC поиск/назначение штаба, создание и
удаление представителя и изменения faction mood исключены. Старые patches
NPC Manager удалены из нового собственного Manager версии 1, HasMissions
по умолчанию false. Контракты сигналов очистки/перепривязки сохранены,
но меняют только собственную ссылку HQ. `check_adapted_manager.py`
проверяет эти границы, SHA и оставшиеся локальные cue-ссылки; XSD проходит.
Собственная таблица metadata и строка фракции теперь создаются перед
дочерними обработчиками, только если отсутствуют. Это повторяет структуру
штатного Setup, не использует его NPC строки и не сбрасывает имеющиеся
данные. Registry lifecycle ещё не подключён; запуск доменных эффектов
не разрешён.

В staged Economy изменён только поиск имеющегося перевозчика:
`Request_Commandeerable_Freighter` больше не требует существования NPC job
или membership в jobtags/warebasket. Он ищет фактические owned ships,
проверяет доступную вместимость нужного товара и сохраняет штатный порядок
по расстоянию/приоритету и проверку добывающего лазера. Доменные приказы
ещё не квалифицированы: нужны непосредственные guards, claims/read-back,
а `Request_Freighter` всё ещё требует обычного платного purchase adapter.
Оба адаптированных файла находятся вне установщика. Этот шаг не закрывает
3.2/3.3 и не разрешает запуск оставшихся NPC эффектов.

Для этого поиска добавлен `CanUseOwnedShip` на документированных свойствах
`libraries/scriptproperties.xml`: фактическая ownership/operational,
`player.controlled`, orders/hasorderloop, priority/override и текущий/default
order. Он вызывается при выборе и повторно непосредственно перед блоком
commandeer/создания штатных приказов. `player.occupiedship` не проверяется:
пассажир не исключает корабль. Пока обрабатываются свободные корабли с Wait;
занятые/неопределённые поведения сохраняются. Это не окончательное решение
для перераспределения: нужны происхождение собственных управляемых приказов,
claims и read-back, чтобы отличать работу нашего Manager от вмешательства
игрока и штатного аварийного поведения. Проверка в игре ещё не проведена.

Первичная provenance добавлена в этом пути: ship blackboard
`$tm_empire_claim` сохраняет cue задачи, sent/unknown, игровое время и реальные
handles `create_order name=...`. Наличие handles проверяется вместе с их
object; не означает выполнения перевозки. Отсутствующий handle переводит
claim в unknown, другой goal не может повторно выбрать этот корабль.
Таймаут/штатный disregard удерживают unknown до согласования; автоматическое
remove_object_commander в этом пути исключено, чтобы не снимать новое
назначение игрока. Согласование завершённых/ручных/аварийных приказов и
освобождение подтверждённых claims ещё не реализованы; этот staged слой
не устанавливается и не закрывает 3.3/3.7.

Добавлен bounded обработчик `OwnedOrderEnded`: он слушает штатные события
finished/cancelled только группы зарезервированных кораблей. Подтверждает
окончательное удаление известного order handle (`not event.param.exists`),
удаляет этот handle из claim и освобождает корабль лишь после окончания всех
известных приказов при отсутствии missing handle. Критическое или временное
прерывание не освобождает claim. Missing остаётся unknown для дальнейшего
согласования. Запись `orders_ended_not_trade_success` означает окончание
приказов, не прибыль/доставку или успешное завершение доменной потребности.
Старые cleanup callbacks могут release commandeer только своего claim,
чтобы поздний таймаут не затронул новую задачу. События подтверждены схемой
`libraries/common.xsd` и native Recon; работа адаптера в игре не проверена.

Guard выбора/эффекта теперь принимает фактический `FactionManagerCue`,
который native Manager передаёт Economy. Перед проверкой корабля он вызывает
`TM_Empire_Runtime.CanActForGovernor`: ValidateBinding, состояние active,
совпадение ManagerCue и текущих actor/station/module обязательны. Снятие
или invalid binding очищают собственную ссылку ManagerCue. Назначение
сотрудника само по себе пока оставляет bound и не разрешает эффекты: создание
единственного квалифицированного экземпляра Manager и перевод в active
ещё не подключены. Эта проверка покрывает только адаптированный путь выбора
перевозчика; остальные домены должны получить ту же границу перед эффектом.

- Manager: собственный lifecycle от Registry; удалить NPC representative/HQ relocation/story/mission effects и записи faction mood/location metadata, использовать фактическую станцию управляющего. Не регистрировать игрока в исходном глобальном FactionManagers.
- Economy: stock анализ сохранить; входы ограничить доступной игроку информацией. NPC SuitableJobs/RequestJobShip заменить допустимым реальным owned ship; изменения собственного cargo/trade/assignment подтверждать native handles.
- Stations/BuildStation: NPC gods/plots/construction budget/subsidies заменить обычными принадлежащими игроку plot/blueprint/builder/accounts/build progress. FinaliseStations не вызывать для бесплатного completion/stock.
- Job_Helper: 0Cr/request_job/create_ship не являются покупкой игрока. Подключить обычные платные offers/build queue с actual ready read-back.
- Military goals: actual relations/видимые угрозы/собственные корабли; перед commandeer/create_order обязательны helm/manual/emergency guards. При отсутствии предпосылки дать потребность/ожидание, не изменить отношения.
- Personnel: в исходном центральном Manager не найден готовый planner найма/семинаров игрока. Использовать штатные Conversations/crew transfer/skill gain и минимально добавить связь кадровой потребности с выбранной доменной целью. Это добавляемая граница, не второй планировщик.

Переписывать native внутренний экономический/военный алгоритм ради удобства не требуется. Каждое из перечисленных мест должно получить обычный игровой путь и доменную проверку, прежде чем own Manager будет активирован.
